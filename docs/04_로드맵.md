## 핵심 결정 사항

- **타겟(라벨) 정의**: 문피아는 실제 매출(KRW)을 공개하지 않음. `pl.serial_end`(유료 전환작) 목록 API의 `nvSumPurchased`(구매수)를 타겟의 원천으로 씀. ⚠️ 이 값은 **작품 전체 누적치**라 유료 회차 수로 나눠야 함 — `target_paid_events_per_episode = purchased_count ÷ 유료 회차 수`(2026-08-13 수정, 근거는 [모델 명세](06_모델.md) 1절). 대여수(`nvSumRented`)는 무료 쿠폰성 이용이 많다고 판단해 제외.
- **매출 환산 = 구매수 × 단가 (모델 밖 단순 곱셈)**: 회차 단가는 작가별 계약에 따라 달라지고 크롤로 확보할 수 없음. 따라서 **모델은 구매수만 예측하고, 단가는 사용자가 입력한 값을 곱함.**

  ```
  회차당 예상 매출(KRW) = 회차당 예측 구매수 × 회차 단가(사용자 입력)
  작품 전체 매출        = 회차당 예상 매출 × 유료 연재 회차 수
  ```

  - 단가는 학습/피처에 일절 개입하지 않음(모델은 단가에 대해 아무것도 학습하지 않음)
  - 앱에 단가 입력 위젯을 두고 사용자가 조정하게 함
  - 곱셈은 선형이므로 단가를 바꿔도 작품 간 **순위는 변하지 않음** — 모델 평가는 구매수 공간에서만 수행하면 충분함
- **피처 기준 `N` = 10 (앞 10화)** — 2026-08-12 샘플로 확정, 2026-08-13 전수 재확인. 학습셋(`pl.serial_end`)과 추론셋(`nv.free`)의 무료 회차 의미가 달라(아래 표) 모든 피처를 **"앞 10화 기준"으로 통일**함.

  | | 학습셋 `pl.serial_end` | 추론셋 `nv.free` |
  |---|---|---|
  | 무료 회차 수 중앙값 | **25화** (10% 23 / 90% 29 — 플랫폼이 정한 티저) | **3화** (전체 회차 = 전부 무료) |
  | 총 회차 수 중앙값 | 200화 | 3화 |
  | 무료 비율 | 5~16% | 100% |

  `total_free_views`를 그대로 쓰면 학습셋에서는 "티저 25화 조회수", 추론셋에서는 "전작 조회수"를 뜻해 완전히 다른 값이 됨(covariate shift). `N=10`이면 **학습셋의 97.4%가 사용 가능**하고 추론 대상은 **11,189건(22.9%)** 확보됨.

  피처 예: `free_views_1_10`(앞 10화 누적 조회수), `retention_1_to_10`(10화/1화 조회수), `retention_1_to_3`(초반 이탈), `likes_1_10`, `comments_1_10`.

  - **추론 대상이 무료작 전체(48,897)가 아니라 회차 10개 이상인 11,189건으로 좁혀짐.** 이는 손실이 아니라 타당한 제약임 — 유료 전환작의 무료 티저가 최소 15화라는 것은 플랫폼이 어느 정도 쌓인 작품만 전환시킨다는 뜻이고, 3화짜리 작품의 전환 매출 예측은 애초에 의미가 없음
  - **"무료 회차 총수"는 피처로 쓸 수 없음** — 유료작에서는 플랫폼이 정한 티저 수(≈25 고정), 무료작에서는 작가가 쓴 전체 분량이라 의미가 다름
- **⚠️ 선택 편향 + 지지구간(support) 불일치**: 학습셋은 "유료 전환에 성공한 작품"만임. 무료작 전체에 그대로 추론하면 애초에 전환하지 못했을 작품에도 성공작 분포를 씌워 체계적으로 과대추정함. 예측값은 **"전환에 성공했을 때의 조건부 기댓값"**으로 해석·표기하고, 앱에서도 그렇게 명시함.

  **2026-08-13 전수 재측정** (학습셋 8,990건 / 추론셋 11,189건):

  | `free_views_1_10` | 추론셋 `nv.free` (11,189건) | 학습셋 `pl.serial_end` (8,990건) |
  |---|---|---|
  | 5% | 37 | 1,586 |
  | 중앙값 | 298 | 185,082 |
  | 95% | 4,951 | 731,535 |
  | 범위 | 0 ~ 351,363 | 12 ~ 2,581,338 |

  - **범위 외삽 문제는 해소됨**: 전수를 받으니 학습셋 최솟값이 248 → 12로 내려가 무료작의 **99.4%가 학습셋 min~max 안**에 들어옴(표본 19건일 때는 55.6%였음). 저트래픽 구간이 채워질 것이라는 예상이 맞았음
  - **그러나 밀도 불일치는 그대로임**: 무료작의 **84%가 학습셋 5분위수(1,586) 미만**이고, 학습셋 5~95% 구간에 들어오는 무료작은 **16.0%**뿐임. 중앙값은 여전히 600배 차이(298 vs 185,082)
  - 다른 피처: `likes_1_10`·`comments_1_10`은 범위 포함 100%, `retention_1_to_10`은 7.5%가 범위 밖(무료작에 1화 대비 10화 조회수가 늘어나는 이상 케이스가 있음 — 최대 4.5)

  → 결론: **min-max 기준으로 예측을 막을 근거는 사라짐.** 대신 학습셋 분위수 기준으로 신뢰도 밴드를 나눔 — (a) 학습셋 5~95% 구간(무료작 16%)은 정상 예측, (b) 5분위수 미만(84%)은 "학습 데이터가 희박한 구간"으로 표기. 앱이 `support_band` 컬럼으로 이 구분을 노출함.

  **티저 조회수 누적 (2026-08-13 추가 측정)**: 이 밀도 격차의 원인 중 하나가 확인됨. 유료작의 무료 회차 조회수는 **전환 이후에도 계속 쌓임**. 나이를 보정해도 일평균 조회수가 학습셋 **105.22** vs 추론셋 **0.48**로 **219배** 차이임(원래 격차 621배 중 나이로 설명되는 건 2.9배뿐). 이는 (a) 애초에 인기작만 전환됐다는 선택 편향과 (b) 전환 후 유입된 독자가 티저를 읽어 조회수가 부풀려진 것이 섞인 결과인데, **스냅샷이 1시점뿐이라 둘을 분리할 수 없음** — 전향적 데이터 수집이 필요한 이유가 이 수치로 뒷받침됨.

  타겟 분포: 총 구매수 기준 중앙값 68,048 / 최대 17,120,177, **회차당으로 환산하면** 중앙값 419 / 최대 26,642 — 어느 쪽이든 스팬이 넓어 `log1p` 학습이 필수임.
- **학습 대상**: `pl.serial_end`(완결, 9,252건, 타겟 확정)만 학습에 사용. `pl.serial`(진행 중, 1,212건)은 구매수가 계속 늘어나는 censored 데이터라 학습 제외, 정성적 검증용으로만 활용.
- **피처 누수 방지 원칙**: 모든 피처는 **무료 회차 데이터에서만** 계산함. `NovelStats`의 누적 집계(`nvSumHit` 등)는 유료작의 경우 무료+유료 기간이 섞여 있어 타겟과 누수 관계이므로 피처로 쓰지 않고 타겟 산출에만 사용함.
- **모델링 순서**: ML(회귀) 먼저, 베이스라인을 유의미하게 못 이길 때만 DL 검토 → **DL 불필요로 판정**(C절).
- **모델 직렬화**: 신규 의존성 없이 표준 `pickle` 사용 (joblib 미도입).
- **다중 시점 대비 — 월 1회 스냅샷, 앞 200페이지** (2026-08-13 확정): `data/processed/`는 `run_id`가 아니라 `snapshot_date`(YYYYMMDD)로 파일을 누적 저장함(덮어쓰지 않음). 주기·범위와 그 근거 수치는 [크롤러](03_크롤러.md)의 "정기 스냅샷 운영" 절에 정리함(요약: 일 단위는 지지구간 작품의 87%가 전 필드 0인 노이즈, 목록이 최신순 정렬이라 30일 내 갱신분 99%가 첫 126페이지 안).

  ⚠️ **스냅샷은 현재 모델의 피처가 될 수 없음.** 두 가지 이유가 겹침.

  1. 학습셋(`pl.serial_end`)은 1회 크롤이고 무료 연재기가 이미 지났음 — 마지막 무료 티저 게시 경과일 중앙값이 **1,942일(5.3년)**임. 추이를 소급해 만들 방법이 없고, `assert_feature_schema`가 학습·추론 피처 동일성을 강제하므로 추이 피처는 추론셋에만 존재하게 되어 투입 불가임
  2. 모델 피처는 회차 단위(`free_views_1_10`)인데 stats 크롤은 작품 단위 `hit_count`만 받음. 추이를 피처화하려면 episodes까지 받아야 함

  그래서 스냅샷의 실제 용도는 **전향적(prospective) 학습셋의 씨앗**임 — 지금 살아있는 무료작을 추적해두면 향후 전환되는 작품에 대해 "전환 이전에 측정된" 피처를 갖게 되고, 이건 선택 편향·지지구간 문제를 동시에 푸는 유일한 경로임(전환하지 못한 작품도 관측되므로). 다만 전환 이벤트가 **연 532건(주 10건) 수준**이라 회수까지 수개월이 걸림.

  전환 감지에는 `pl.serial`(진행 중) 크롤이 필요함: 21.4시간 새 `nv.free`에서 69건이 빠졌지만 그중 `pl.serial_end`에 나타난 건 **0건**이었음 — 갓 전환된 작품은 완결이 아니라 연재 중 섹션으로 감.

## A. 라벨 데이터 크롤러 — **완료** (2026-08-12)

**별도 `paid_runner.py`를 만들지 않고 기존 `run_crawl`을 확장함.** 체크포인트/abort/resume/limit 로직을 그대로 재사용하고, 유료 섹션의 타겟인 구매수는 어차피 목록 API 응답에 들어 있어 같은 순회에서 얻을 수 있기 때문임.

```python
run_crawl(config, max_pages, novel_limit, out_dir, resume=False,
          prefix="",            # "paid_" -> paid_novels_*.csv
          collect_stats=False)  # 목록 item -> NovelStats(구매수) 동시 저장
```

`scripts/crawl_munpia.py`에 `--section` / `--prefix` / `--collect-stats`가 대응함. 목록 순회는 `iter_list_pages` → `iter_list_page_items`로 바뀜(item dict에서 `nvSrl`과 구매수를 함께 사용).

- 장르가 목록 API에서는 숫자 코드(`nvGnMain`)뿐이라 무료작 데이터셋(문자열 `genres`/`tags`)과 스키마를 맞추기 위해 `novel-detail` 상세 호출은 그대로 유지함
- **저장 위치**: `--output-dir data/raw/paid --prefix paid_`
  - ⚠️ `data/raw/`를 그대로 쓰면 안 됨: `CrawlCheckpoint.find_latest`는 `base_dir` 안의 `.processed_novel_ids_*.log`를 **mtime으로만** 고르므로, nv.free 체크포인트와 같은 디렉토리에 있으면 `--resume` 시 엉뚱한 체크포인트를 집음
  - 같은 이유로 `pl.serial`과 `pl.serial_end`도 `--output-dir`를 나눔. 그러면 체크포인트 키에 section을 넣는 수정이 불필요함

### 회차 호출 최적화 (`--free-chapters-only`)

첫 유료(`free=false`) 회차를 만나면 회차 수집을 중단함. 샘플 20건 검증에서 19건이 무료 구간 완전 연속이었고, 예외 1건은 **마지막 회차에 붙은 완결 후기**였음 — 누락되는 건 전체 무료 492화 중 0.2%이고 티저가 아니라 피처로 써서도 안 되는 회차임. 작품당 평균 281화 → 앞 25화만 받으므로 회차 페이지 요청이 약 3.5페이지 → 1페이지로 줄어 **크롤 시간이 9시간대 → 2시간대**가 됨.

구현: `fetch_novel_bundle(..., free_chapters_only=True)`가 `access_type == "PAID"`를 만나면 그 회차를 담지 않고 중단함. 선행 연속 무료 구간만 남으므로 완결 후기가 자동으로 걸러짐(피처 계산이 기대하는 것과 일치). `chapter_count`는 `novel-detail` 응답에서 오므로 총 회차 수는 그대로 보존됨.

## B. 정제/피처 엔지니어링 (`service/`) — **완료** (2026-08-12)

```bash
uv run python scripts/build_processed_dataset.py --free       # 추론셋 11,189건
uv run python scripts/build_processed_dataset.py --labeled \
  --data-dir data/raw/paid --stats-dir data/raw/paid --prefix paid_   # 학습셋 8,990건
```

출력은 `data/processed/{free|labeled}_dataset_{YYYYMMDD}.csv`. 두 데이터셋의 피처 컬럼이 동일함을 `assert_feature_schema`가 저장 전에 강제함.

| 모듈 | 역할 |
|---|---|
| `raw_loader.py` | `data/raw/`에서 각 CSV 접두사별 최신 `run_id` 파일을 찾아 로드 |
| `episode_features.py` | `compute_episode_features(episodes_df, n=10)` — **앞 10화 기준** 집계(`free_views_1_10`, `retention_1_to_10`, `retention_1_to_3`, `likes_1_10`, `comments_1_10`). 무료작/유료작 데이터셋에 동일 함수 적용. 무료 회차가 10개 미만인 작품은 제외 |
| `novel_features.py` | `Novel` 정적 필드(`genres`) + episode_features inner join. 범주형 인코딩은 여기서 하지 않고 모델 파이프라인(`ColumnTransformer`)에 위임. `LEAKY_COLUMNS`(`total_view_count`/`chapter_count`/`like_count`/`preference_count`)는 유료작에서 무료+유료 기간이 섞여 타겟과 누수 관계이므로 제외. `NovelStats`의 `good_count`/`prefer_count`도 "현재 시점 스냅샷"이라 유료작의 무료 시기 값만 분리할 수 없어 같은 이유로 제외. `EXCLUDED_STATIC_COLUMNS`(`tags`/`serialization_status`)는 아래 "범주형 피처" 참고 |
| `target_builder.py` | `NovelStats` → `target_paid_events_per_episode`(**회차당** 구매수) 산출. `paid_episode_counts()`로 유료 회차 수를 구해 나눔. 구매수 0/결측·회차수 불명 작품은 제외하고 제외 건수를 반환. 매출 환산(× 단가)은 여기서 하지 않음 — 앱이 사용자 입력 단가로 곱함 |
| `schema.py` | `FEATURE_COLUMNS`, `assert_feature_schema(df, with_target=...)` — 컬럼 **누락과 예상 밖 컬럼을 모두** 검출해 학습/추론 간 피처 어긋남을 막음 |
| `scripts/build_processed_dataset.py` | `--free`(추론 대상, 타겟 없음) / `--labeled`(학습셋). `snapshot_date`로 누적 저장 |

**메타데이터 vs 피처**: `leading_free_episodes`(선행 무료 구간 길이)는 데이터셋에 싣되 **피처에서는 뺌** — 유료작은 플랫폼이 정한 티저 수(≈25 고정), 무료작은 작가가 쓴 전체 분량이라 의미가 다름.

### 범주형 피처 (2026-08-13 수정)

모델링 착수 전 두 컬럼을 피처에서 제거함. 두 데이터셋의 분포를 나란히 재보고 나서야 드러난 문제임.

| 컬럼 | 학습셋 `pl.serial_end` | 추론셋 `nv.free` | 판정 |

재발 방지로 `tests/service/test_schema.py::test_degenerate_categoricals_stay_out_of_features`가 `EXCLUDED_STATIC_COLUMNS`가 `FEATURE_COLUMNS`로 되돌아오는 것을 막음.

### 튜닝 조사 결과 (2026-08-13)

"테스트 데이터 성능이 어느 정도인지 파악하고 계획을 세우라"는 요청으로 조사함. **결론은 하이퍼파라미터가 아니라 타겟·피처 정의가 병목이라는 것**이었고, 실제로 타겟 정의를 고쳐 큰 개선을 얻음.

아래 수치는 **타겟을 고치기 전(총 구매수 기준)** 조사한 것임. 이후 회차당 타겟으로 전환하며 성능이 크게 좋아졌으므로(logRMSE 0.9036 → 0.6947) 절대값은 현재와 다르지만, **"하이퍼파라미터는 여력이 없고 정의가 지렛대"라는 결론은 그대로 유효함.**

**하이퍼파라미터 튜닝 여력은 거의 없었음**: 25조합 랜덤서치로 CV logRMSE 0.9221 → 0.9172(0.5%), holdout MdAPE 51.3% → 51.1%. 반면 **타겟을 회차당으로 바꾼 것만으로 23% 개선**됨(0.9036 → 0.6947).

**N(피처 기준 회차 수)도 지렛대임** (아래는 총 구매수 타겟 기준 측정, **회차당 타겟으로는 재측정하지 않았음**):

| N | 학습셋 | 추론 대상 | logRMSE | MdAPE | Spearman |
|---|---|---|---|---|---|
| 5 | 9,084 | 18,734 | 0.9487 | 53.0% | 0.894 |
| **10 (현재)** | 8,990 | 11,189 | 0.9036 | 51.3% | 0.892 |
| 20 | 8,800 | **5,737** | **0.8294** | **47.4%** | 0.903 |
| 25 | 7,818 | 4,486 | 0.8457 | 48.1% | 0.906 |

N=20이 8.2% 개선이지만 검색 대상이 절반이 됨. N=25는 오히려 나빠져 20이 최적점임. **선택(N=10 유지 / N=20 전환 / 2단 구성)은 미결.**

- **수치 피처에 `log1p`가 필수임**: `free_views_1_10`/`likes_1_10`/`comments_1_10`이 3~7자릿수에 걸쳐 치우쳐 있어, 원공간 그대로 넣으면 `Ridge`가 자기 단일회귀 베이스라인보다도 나빴음(총 구매수 타겟 기준 1.226 vs 1.111). `impute_log_scale=True`가 중앙값 대치 → `log1p` → 표준화를 붙임. 회차당 타겟에서도 `Ridge` 0.7964 < 베이스라인 0.8652로 순서가 유지됨. 트리 계열은 단조 변환에 불변이라 불필요하고, `HistGradientBoostingRegressor`는 NaN도 네이티브로 처리하므로 전처리 없이 씀(`retention_*`에 1화 조회수가 0인 작품의 NaN이 있음)
- **밴드별 에러**(회차당 타겟, holdout 재측정): 정상 1,634건 MdAPE **40.3%** / 희박(하한 미만) 71건 **44.9%** / 희박(상한 초과) 93건 40.2%. 학습셋 안에서는 밴드 간 차이가 크지 않지만, **추론셋은 84%가 희박(하한) 밴드**라 이 수치를 그대로 옮길 수 없음 — 학습셋의 희박 표본은 71건뿐임
- **모델 직렬화**: 표준 `pickle`(joblib 미도입). `CountVectorizer(analyzer=...)`에 넘기는 토큰 분할 함수는 반드시 **모듈 수준 함수**여야 함 — 람다로 두면 pickle이 깨짐(`tests/service/test_model_training.py::test_fitted_pipeline_is_picklable`가 가드)

**Streamlit 계획을 폐기함.** 수요자가 비전공자 작가인데 `streamlit run`은 Python 설치를 전제하므로 배포 수단이 될 수 없음(호스팅하면 되지만 "실제 서비스가 아니다"라는 방향과 맞지 않음). `pages/`와 `streamlit` 의존성을 제거함.

### 왜 정적 HTML로는 안 되는가

예측은 이미 오프라인에서 끝나 있어(`predictions_*.csv`, CSV 1.09MB) 조회만 하면 브라우저로 충분함. 그러나 **조회 전용으로는 정작 쓸 사람이 자기 작품을 못 찾음** — 추론셋의 최근 30일 내 갱신 작품은 11.0%(1,227건)뿐이고 마지막 회차 게시 경과일 중앙값이 582일임. 지금 연재 중이라 유료 전환을 고민하는 작가는 스냅샷에 없을 확률이 높음.

그래서 **작품 주소 입력 → 실시간 크롤·예측** 경로를 넣었고, 이 경로가 런타임에 sklearn을 요구해 Python 동봉이 불가피해짐.

- **onefile 단일 exe**(72.1MB) — 작가에게 **파일 하나만** 보내면 됨. 처음에는 onedir(폴더 172MB / zip 72.5MB)로 만들었으나, `MunpiaRevenue.exe`가 실행기일 뿐이고 Python 런타임·sklearn·번들이 전부 `_internal/`(151.4MB)에 있어 **exe만 넘기면 실행되지 않음**(실측 exit code -1). 전달 편의를 위해 onefile로 전환함
- **onefile의 대가와 대응**: **매 실행마다** ~150MB를 `%TEMP%`에 푸느라 메인 창까지 **7~8초**가 걸림(실측 1회차 7.6초 / 2회차 7.2초 — OS 파일 캐시가 붙어도 압축 해제 자체는 매번 함. onedir은 2.3초였음). 그동안 아무 반응이 없으면 작가가 계속 더블클릭해 창이 여러 개 뜨므로 **스플래시를 띄움** — 실측 **0.4초** 만에 표시됨(`scripts/make_splash.py`가 이미지를 만들고 spec의 `Splash()`가 묶음. `app/main.py`의 `close_splash()`가 메인 창 준비 후 닫고, 번들 로드 실패 경로에서도 반드시 닫음)

  > ⚠️ 측정 함정: PyInstaller onefile은 부트로더(부모)와 실제 앱(자식)이 별도 프로세스라 부모의 `MainWindowHandle`은 계속 0임. 또 스플래시가 먼저 뜨므로 "첫 창"을 재면 0.4초라는 잘못된 값이 나옴. **창 크기나 제목으로 메인 창을 구분해서** 재야 함
- **패키징 함정**: 모델 pkl 언피클 시 `CountVectorizer(analyzer=...)`가 `service.model_training.genre_tokens`를 참조하는데 `app/main.py`가 이 모듈을 직접 import하지 않음. spec의 `hiddenimports`에 넣지 않으면 **배포본에서만** 실시간 분석이 죽음. `--selftest`가 `model.predict`까지 돌려 이걸 잡음(빌드 스크립트가 `RESULT: OK`를 확인하고 아니면 실패시킴)
- **URL 파싱**: 문피아 공개 작품 페이지 URL 형식이 조사 기록에 없어(문서에는 API 경로만 있음) 형식을 하드코딩하지 않음. 붙여넣은 문자열에서 4자리 이상 숫자 중 가장 긴 것을 후보로 잡고 실제 API 호출로 검증함. 작품 번호를 직접 입력해도 동작함
- **실패를 예외가 아니라 값으로 다룸**(`PredictionResult.ok/reason`). `fetch_novel_bundle`은 대량 크롤에서 문제 작품을 건너뛰려고 네트워크 오류까지 삼켜 `None`을 돌려주므로(차단만 예외로 올라옴) "작품 없음"과 "인터넷 끊김"을 **구분할 수 없음** — 안내 문구가 두 원인을 모두 언급함
- 서명되지 않은 exe라 SmartScreen이 "알 수 없는 게시자" 경고를 띄움. 코드 서명 인증서 없이는 제거 불가라 `사용법.txt`에 "추가 정보 → 실행" 절차를 적어 동봉함

## F. 크롤러 안정성(워치독) — **완료** (`scripts/watch_and_resume.ps1`, 2026-08-12)

```powershell
# 유료 라벨 크롤을 감시하며 실행 (사용자 터미널에서 직접)
powershell -File scripts/watch_and_resume.ps1 `
  -OutputDir data/raw/paid `
  -ExtraArgs '--section pl.serial_end --prefix paid_ --collect-stats --free-chapters-only --max-pages 0 --novel-limit 0 --delay 0.8'

# 실제 재시작 없이 계산된 --start-page만 확인
powershell -File scripts/watch_and_resume.ps1 -OutputDir data/raw/paid -ExtraArgs '...' -DryRun
```

⚠️ **에이전트 세션의 백그라운드로 띄우지 말 것** — 워치독 자신이 같은 수명 제한에 걸림.

**배경**: 장시간 크롤 중 백그라운드 프로세스가 여러 차례 강제 종료됨(관찰된 간격: 9시간 → 1.7시간 → 수 분 단위로 불규칙). 종료 시점의 여유 메모리는 3.67GB/15.7GB, 크롤러 프로세스는 731MB로 안정적이었고 로그에 에러·abort가 없었음 — 즉 **메모리 부족이 아니라 실행 환경의 프로세스 수명 제한**으로 보임. `clawler/http_client.py`의 tenacity 재시도는 개별 요청 실패에는 대응하지만, OS/환경이 프로세스 자체를 강제 종료하는 상황은 프로세스 내부 로직으로 막을 수 없음.

**동작**:

- 주기적으로(기본 300초) 다음을 확인함
  1. 대상 프로세스가 살아있는지 — `Get-CimInstance Win32_Process`로 커맨드라인 매칭
  2. 체크포인트 로그의 줄 수가 이전 확인 시점보다 늘었는지
- 프로세스가 죽어있거나, 살아있어도 일정 시간 이상 체크포인트가 늘지 않으면(멈춤으로 간주) `--resume`으로 재시작함
- **재시작 시 `--start-page`를 계산해 넘김**: 체크포인트 줄 수를 이미 세고 있으므로 `[줄 수 / 20] - 여유분`으로 시작 페이지를 계산함. 이게 없으면 절반 진행 상태에서 재개할 때 앞 페이지 재스캔에만 20분 이상을 버림
- **무한 재시작 방지**: **진전 없는 연속 재시작**이 `-MaxRestarts`회를 넘으면 워치독 자체를 멈춤 — 근본 원인이 있는데 계속 자동 재시작만 하면 문제를 숨기게 되므로
  - ⚠️ 처음에는 "5분 내 3회"처럼 **시간 창**으로 셌는데, 점검 주기(기본 300초)가 그 창과 같아 한 창에 한 번밖에 안 들어가 **가드가 영영 발동하지 않았음**(2026-08-12, 잘못된 인자로 15분간 3회 재시작하며 방치됨). 시간이 아니라 "체크포인트가 늘었는가"로 세야 함
  - **즉시 실패 감지**: 재시작한 프로세스가 `-StartupCheckSeconds`(기본 20초) 안에 종료되면 인자 오류로 보고 다음 점검 주기를 기다리지 않고 바로 멈춘 뒤, 직접 실행해볼 명령을 출력함
  - **`-ExtraArgs` 개행 정규화**: 명령을 여러 줄에 걸쳐 붙여넣으면 문자열에 개행이 섞여 토큰이 `--collect-stats\n`이 되고 argparse가 `unrecognized arguments`로 거부함. 스크립트가 공백을 정규화해 흡수함
