# 로드맵 (데이터 파이프라인 / 모델링 / 대시보드 / 테스트)

크롤러 이후 남은 작업의 설계를 정리한다. 세부 구현 시 참고용.

## 핵심 결정 사항

- **타겟(라벨) 정의**: Munpia는 실제 매출(KRW)을 공개하지 않는다. `pl.serial`/`pl.serial_end`(유료 전환작) 목록 API의 `nvSumPurchased`(구매수)를 타겟으로 쓴다 — `target_paid_events = purchased_count`. 대여수(`nvSumRented`)는 무료 쿠폰성 이용이 많다고 판단해 제외.
- **매출 환산 = 구매수 × 단가 (모델 밖 단순 곱셈)**: 회차 단가는 작가별 계약에 따라 달라지고 크롤로 확보할 수 없다. 따라서 **모델은 구매수만 예측하고, 단가는 사용자가 직접 입력받아 곱한다.**

  ```
  예상 매출(KRW) = 예측 구매수(target_paid_events) × 회차 단가(사용자 입력)
  ```

  - 단가는 학습/피처에 일절 개입하지 않는다(모델은 단가에 대해 아무것도 학습하지 않음).
  - 대시보드(`pages/_predictions.py`)에 단가 입력 위젯을 두고, 기본값과 함께 사용자가 조정할 수 있게 한다.
  - 곱셈은 선형이므로 단가를 바꿔도 작품 간 **순위는 변하지 않는다** — 모델 평가는 구매수 공간에서만 수행하면 충분하다.
- **⚠️ 학습셋/추론셋의 피처 의미 불일치 (착수 전 반드시 확인)**: 학습은 `pl.serial_end`(유료), 추론은 `nv.free`(무료)에 하면서 "피처는 무료 회차에서만" 원칙을 적용하면, 유료작의 무료 회차는 프로모션용 앞부분 몇 화인 반면 무료작의 무료 회차는 작품 전체다. `total_free_views`가 양쪽에서 전혀 다른 것을 의미하게 된다(covariate shift). **대응**: 라벨 크롤 A의 샘플 검증 단계에서 `pl.serial_end`의 무료 회차 수 분포를 먼저 확인하고, 피처를 **"앞 N화 기준"으로 통일**(예: 첫 20화 누적 조회수, 1화→20화 잔존률)해 양쪽 정의를 맞춘다. N은 유료작의 무료 회차 수 분포 하위 분위수에서 정한다.
- **⚠️ 선택 편향**: 학습셋은 "유료 전환에 성공한 작품"만이다. 무료작 전체에 그대로 추론하면 애초에 전환하지 못했을 작품에도 성공작 분포를 씌워 체계적으로 과대추정한다. 예측값은 **"전환에 성공했을 때의 조건부 기댓값"**으로 해석·표기하고, 대시보드에서도 그렇게 명시한다.
- **학습 대상**: `pl.serial_end`(완결, ~9,249건, 타겟 확정)만 학습에 사용. `pl.serial`(진행 중, ~1,212건)은 구매수가 계속 늘어나는 censored 데이터라 학습 제외, 정성적 검증용으로만 활용.
- **피처 누수 방지 원칙**: 모든 피처는 **무료 회차 데이터에서만** 계산한다. `NovelStats`의 누적 집계(`nvSumHit` 등)는 유료작의 경우 무료+유료 기간이 섞여 있어 타겟과 누수 관계이므로 피처로 쓰지 않고 타겟 산출에만 사용한다.
- **모델링 순서**: ML(회귀) 먼저, `HistGradientBoostingRegressor`가 `total_free_views` 단일 피처 베이스라인을 유의미하게 못 이기고 에러 분석으로 데이터 문제가 아님이 확인될 때만 DL 검토.
- **모델 직렬화**: 신규 의존성 없이 표준 `pickle` 사용 (joblib 미도입).
- **다중 시점 대비**: `data/processed/`는 `run_id`가 아니라 `snapshot_date`(YYYYMMDD)로 파일을 누적 저장(덮어쓰지 않음). 다만 **현재 확보된 무료작 스냅샷은 2026-08-10 하나뿐**이라 시계열 피처(조회수 추이·이탈률 추이)는 아직 만들 수 없다. [프로젝트 개요](02_프로젝트개요.md)가 참고 프로젝트의 주된 제약으로 짚은 부분이므로, 저비용인 `scripts/crawl_munpia_stats.py`(전체 30분대)만이라도 주기적으로 돌려 2시점 이상을 먼저 확보한다 — 늦게 시작할수록 간격을 벌 수 없다.

## A. 라벨 데이터 크롤러 (`clawler/paid_runner.py`, `scripts/crawl_munpia_paid.py`)

- `CrawlConfig.section`을 `pl.serial`/`pl.serial_end`로 바꿔가며 목록만 순회(`iter_list_page_items`)하면 구매수를 포함한 item dict를 얻는다.
- 장르가 목록 API에서는 숫자 코드(`nvGnMain`)뿐이라 무료작 데이터셋(문자열 `genres`/`tags`)과 스키마를 맞추기 위해 `novel-detail` 상세 호출은 그대로 유지한다.
- 회차 호출은 비용 절감을 위해 **처음 유료(`free=false`) 회차를 만나면 중단**하는 최적화를 적용할 계획 — 단, "무료 회차가 항상 앞쪽에 연속된다"는 가정이므로 구현 전 20~30개 샘플로 전체 회차를 받아 검증 후 확정한다.
- **샘플 검증 시 같이 확인할 것**: 각 샘플의 **무료 회차 수 분포**. 위 "학습셋/추론셋 피처 의미 불일치" 대응에 쓸 `N`(앞 N화 기준)을 여기서 정한다. 이 확인 없이 B의 피처 엔지니어링으로 넘어가지 않는다.
- **저장 위치**: `CrawlRepository(prefix="paid_")` + **`data/raw/paid/` 디렉토리 분리**(`data/raw/paid/paid_novels_*.csv` 등).
  - ⚠️ `data/raw/`를 그대로 쓰면 안 된다: `CrawlCheckpoint.find_latest`는 `base_dir` 안의 `.processed_novel_ids_*.log`를 **mtime으로만** 고르므로, nv.free 체크포인트와 같은 디렉토리에 있으면 `--resume` 시 엉뚱한 체크포인트를 집는다. `clawler/stats_runner.py`의 docstring이 경고하는 것과 같은 함정이다.
- **체크포인트 키에 section 반영 필요**: 한 디렉토리에서 `pl.serial`과 `pl.serial_end`를 순차로 돌 계획이라면 키를 `f"{section}:{novel_id}"`로 해야 한다. 단, **현재 `CrawlCheckpoint`와 `runner.py`에는 section 개념이 자체가 없으므로 구현 시 둘 다 수정해야 한다**(지금 코드로는 불가). 섹션별로 `--output-dir`를 나누면 이 수정 없이도 해결된다 — 그쪽이 더 간단하다.
- **실행 시점**: nv.free 크롤이 끝난 뒤 시작(동시 부하 방지). 예상 규모 약 10,461건, 6~9시간대.

## B. 정제/피처 엔지니어링 (`service/`)

| 모듈 | 역할 |
|---|---|
| `raw_loader.py` | `data/raw/`에서 각 CSV 접두사별 최신 `run_id` 파일을 찾아 로드 |
| `episode_features.py` | `compute_episode_features(episodes_df)` — 무료 회차 기준 집계(조회수/좋아요/댓글, `view_retention_ratio` 등). 무료작/유료작 데이터셋에 동일 함수 적용 |
| `novel_features.py` | `Novel` 정적 필드(장르/태그/연재상태) + episode_features join. 범주형 인코딩은 여기서 하지 않고 모델 파이프라인(`ColumnTransformer`)에 위임. **`NovelStats`의 `good_count`(좋아요)/`prefer_count`(선호작=구독)도 후보 피처** — `scripts/crawl_munpia_stats.py`로 무료작/유료작 모두 동일하게 수집 가능(저비용, [크롤러](03_크롤러.md) 참고). 단, 목록 API 값은 "현재 시점 스냅샷"이라 무료/유료 시기가 구분되지 않으므로 유료작에 쓸 때는 B의 누수 방지 원칙(핵심 결정 사항 참고)을 그대로 적용 — 유료작의 `good_count`/`prefer_count`는 무료 시기 값만 분리해낼 수 없어 피처로 쓰지 않거나 신중히 다뤄야 함 |
| `target_builder.py` | `NovelStats` → `target_paid_events`(구매수) 산출. 매출 환산(× 단가)은 여기서 하지 않는다 — 대시보드가 사용자 입력 단가로 곱한다 |
| `schema.py` | `FEATURE_COLUMNS`, `assert_feature_schema(df)` — 무료/유료 데이터셋과 추론 스크립트가 공통으로 검증 |
| `build_processed_dataset.py` | `build_free_dataset()`(추론 대상, 타겟 없음) / `build_labeled_dataset()`(학습셋) |

## C. 모델링 (`research/`, `scripts/`)

- 분할: `pl.serial_end` 80/20, 타겟 분위수 층화, 5-fold CV
- 타겟 변환: `log1p`로 학습, `expm1`로 역변환. 지표: 로그공간 RMSE/R²(모델 비교), 원공간 MAE·MdAPE, Spearman 순위상관(다운스트림이 "순위 매기기"이므로). 모든 평가는 **구매수 공간**에서 한다(단가는 상수배라 순위·상대오차에 영향 없음)
- 베이스라인: 평균/중앙값, `total_free_views` 단일회귀
- 후보(순서대로): `Ridge`/`ElasticNet` → `RandomForestRegressor` → `HistGradientBoostingRegressor`(NaN 네이티브 처리, 유력 후보)
- `research/01_eda.ipynb` → `02_baseline_and_ridge.ipynb` → `03_tree_ensembles.ipynb`, 로직은 `service/model_training.py`로 승격
- `scripts/train_revenue_model.py`(학습+저장) / `scripts/predict_conversion_revenue.py`(무료작에 적용, 대시보드가 이 출력을 읽음)

## D. 대시보드 (`pages/`)

Streamlit `st.navigation`/`st.Page` API로 3페이지 구성:
- `pages/app.py`(진입점) → `_overview.py`(무료작 현황·학습셋 분포 비교), `_predictions.py`(예측 순위/필터 + **회차 단가 입력 위젯** → 예상 매출 = 예측 구매수 × 단가), `_model_performance.py`(지표·베이스라인 비교)
- `_predictions.py`에는 예측값이 "**유료 전환에 성공했을 때의** 조건부 기댓값"이라는 주석을 UI에 노출한다(핵심 결정 사항의 선택 편향 참고).

## F. 크롤러 안정성(워치독) — 설계만, 구현은 유료 크롤 시작 시

**배경**: nv.free 크롤 진행 중, 백그라운드 프로세스가 여러 차례 강제 종료됐다(관찰된 간격: 9시간 → 1.7시간 → 수 분 단위로 불규칙). 원인은 크롤러 코드 버그가 아니라 **로컬 PC의 여유 메모리 부족**으로 추정(다른 프로세스, 예: Jupyter 커널이 RAM 대부분 점유 — 확인 시점 기준 여유 메모리 약 1GB/16GB). `clawler/http_client.py`의 tenacity 재시도는 개별 요청 실패에는 대응하지만, OS/환경이 프로세스 자체를 강제 종료하는 상황은 프로세스 내부 로직으로 막을 수 없다. 지금까지는 종료될 때마다 수동으로 `--resume` 재실행해 대응했다(체크포인트 덕분에 데이터 유실은 없었음).

**설계안**: `scripts/watch_and_resume.ps1` (PowerShell 워치독, 유료 크롤 실행 시 함께 도입 — 지금 nv.free 크롤에는 적용하지 않음)

- 주기적으로(예: 5분 간격) 다음을 확인:
  1. 대상 프로세스(`crawl_munpia.py` 또는 `crawl_munpia_paid.py`)가 살아있는지 — `Get-CimInstance Win32_Process`로 커맨드라인 매칭
  2. 체크포인트 로그(`data/raw/.processed_novel_ids_{run_id}.log`, 유료 크롤은 `data/raw/paid/` 하위)의 줄 수가 이전 확인 시점보다 늘었는지
- 프로세스가 죽어있거나, 살아있어도 일정 시간(예: 10분) 이상 체크포인트가 늘지 않으면(멈춤으로 간주) `--resume`으로 재시작
- **무한 재시작 방지**: 재시작 횟수와 시각을 로그 파일에 기록하고, 짧은 시간 내(예: 5분 내 3회) 반복되면 워치독 자체를 멈추고 콘솔에 알림만 남긴다 — 근본 원인(메모리 부족 등)이 있는데 계속 자동 재시작만 하면 문제를 숨기게 되므로.
- 실행: `powershell -File scripts/watch_and_resume.ps1 -RunId <run_id> -ScriptPath scripts/crawl_munpia_paid.py`처럼 대상 스크립트/run_id를 인자로 받도록 설계.
