# 크롤러

문피아 목록의 작품/회차 메타데이터를 수집해 `data/raw/`에 CSV로 저장함.

## 실행

```bash
uv run python scripts/crawl_munpia.py --max-pages 1 --novel-limit 5   # 소규모 테스트
uv run python scripts/crawl_munpia.py --max-pages 0 --novel-limit 0 --delay 0.8 --resume   # 전체 크롤

# 유료 섹션(라벨 데이터) — 출력 디렉토리를 반드시 분리. 워치독과 함께 실행 권장
powershell -File scripts/watch_and_resume.ps1 -OutputDir data/raw/paid `
  -ExtraArgs '--section pl.serial_end --prefix paid_ --collect-stats --free-chapters-only --max-pages 0 --novel-limit 0 --delay 0.8'
```

> **장시간 크롤은 워치독과 함께 돌릴 것.** 2026-08-12 스냅샷 크롤이 30~50분 지점에서 두 차례 외부 종료됨(여유 메모리 3.67GB/15.7GB, 크롤러 731MB, 로그에 에러 없음 — 메모리가 아니라 실행 환경의 프로세스 수명 제한으로 추정). `scripts/watch_and_resume.ps1`이 프로세스 생존과 체크포인트 증가를 감시해 `--resume --start-page`로 재시작함. 설계는 [로드맵 F](04_로드맵.md) 참고.

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--section` | `nv.free` | 목록 섹션 (`nv.free`/`pl.serial`/`pl.serial_end` 등) |
| `--prefix` | `""` | 출력 파일명 접두사 (`paid_` → `paid_novels_{run_id}.csv`) |
| `--collect-stats` | off | 목록 API의 구매수/좋아요 등을 `novel_stats` CSV로 함께 저장 (유료 섹션의 타겟) |
| `--free-chapters-only` | off | 첫 유료 회차에서 회차 수집 중단. 유료 섹션에서 회차 페이지 요청이 3~5회 → 1회로 줄어 크롤 시간이 9시간대 → 2시간대가 됨 |
| `--max-pages` | 1 | 목록 페이지 최대 크롤링 수. **`0`이면 전체** (nv.free 기준 약 2,442페이지) |
| `--novel-limit` | 10 | 상세정보를 수집할 최대 작품 수. `0`이면 제한 없음 |
| `--output-dir` | `data/raw` | CSV 출력 디렉토리 |
| `--delay` | 1.2초 | 요청 간 지연 시간(초) |
| `--resume` | off | `--output-dir`에서 가장 최근 체크포인트를 찾아 이어서 실행 |
| `--start-page` | 1 | 목록 시작 페이지. 재개 시 앞 페이지 재스캔을 건너뜀 (아래 참고) |
| `--log-level` | INFO | `DEBUG`로 실행하면 요청별 타이밍 확인 가능 |

> ⚠️ **`--max-pages` 기본값은 1임.** 전체 크롤인데 빠뜨리면 조용히 1페이지(20건)만 수집하고 정상 종료함. 두 크롤러 모두 동일하니 `--max-pages 0`을 반드시 붙일 것.

## 아키텍처

- `clawler/` — HTTP·오케스트레이션만 담당 (파일 I/O 없음)
  - `config.py` — `CrawlConfig`: 엔드포인트/헤더/딜레이/재시도 설정, `FORBIDDEN_PATH_PREFIXES`로 robots.txt Disallow 경로를 코드 레벨에서 원천 차단. `section` 필드(기본 `nv.free`)로 목록 카테고리 전환 — 아래 "섹션별 목록" 참고
  - `http_client.py` — `MunpiaHttpClient`: 요청마다 딜레이, 5xx/타임아웃 재시도(tenacity), 403/429는 재시도 없이 즉시 `BlockedByServerError`. `BlockedByServerError`/`ForbiddenPathError`는 작품 하나의 문제가 아니므로 skip 대상에서 제외되고 크롤 전체를 중단시킴(`CrawlSummary.aborted`)
  - `list_crawler.py` — 목록 페이지를 순회. `iter_list_pages`(novel_id만) / `iter_list_page_items`(구매수 등 원본 필드 포함 전체 item dict)
  - `detail_crawler.py` — 작품 상세 + 회차 목록을 가져와 `Novel`/`Episode` 엔티티로 변환. 응답에서 `result.novelInfo`/`result.list` 경로를 못 찾으면 `UnexpectedResponseError`를 던짐 — API 스키마가 바뀌었을 때 빈 값 행을 조용히 쌓지 않기 위함(작품 단위로 skip되어 `skipped_novel_ids`에 남고 WARNING 로그가 즉시 뜸)
  - `checkpoint.py` — `CrawlCheckpoint`: 처리 완료된 novel_id를 append-only 로그(`.processed_novel_ids_{run_id}.log`)에 기록해 재개 지원
  - `runner.py` — 전체 흐름 조율, 작품 단위로 CSV에 즉시 append(중단돼도 그때까지 수집분은 보존됨). `prefix`로 출력 파일명을 분리하고, `collect_stats=True`면 목록 item에서 `NovelStats`(구매수 등)도 같은 순회에서 저장함 — 유료 섹션은 타겟(`nvSumPurchased`)이 목록 API에만 있어 이 옵션으로 타겟과 피처를 한 번에 얻음
  - `stats_runner.py` — 목록 페이지만 순회하는 저비용 통계 크롤(아래 "통계 백필")
- `entity/` — JSON 응답 → dataclass 매핑 (방어적 `.get()` 파싱, 네트워크 없이 단위 테스트 가능): `Novel`, `Episode`, `NovelStats`(목록 API의 구매/대여/조회 집계 필드)
- `repository/` — dataclass → CSV 저장. `CrawlRepository(run_id, base_dir, prefix="")` — `prefix`로 무료/유료 크롤 출력을 분리함

## 섹션별 목록 (`section` 파라미터)

목록 AJAX 엔드포인트는 `section` 값에 따라 다른 카테고리를 반환함. 확인된 값:

| section | 의미 | 규모 | 구매/대여 수(`nvSumPurchased`/`nvSumRented`) |
|---|---|---|---|
| `nv.free` | 무료 자유연재 (수집 완료) | 48,836건* | 항상 0 |
| `nv.pro` / `nv.regular` | 작가연재 / 일반연재(무료 단계) | 3,070 / 15,862건 | 항상 0 |
| `pl.serial` | 선연재(독점 유료), 진행 중 | 1,212건 | 채워짐 (단, 진행 중이라 계속 증가하는 censored 값) |
| `pl.serial_end` | 완결 유료 (수집 완료) | 9,249건* | 채워짐 (확정값) |

\* 규모는 목록 API가 응답에 담아주는 `count` 값(크롤 **시작 시점** 스냅샷)임. 실제 수집 결과는 각각 **48,897건 / 9,252건**으로 더 많은데, 장시간 크롤 도중 신규 작품이 등록되며 목록이 늘어난 결과임. 두 숫자가 다른 것은 정상이며 재크롤 시에도 정확히 일치하지 않음.

`pl.serial`(진행 중)은 구매수가 계속 늘어나는 censored 데이터라 학습에서 제외하고 정성적 검증용으로만 활용함 — 상세는 [로드맵](04_로드맵.md) 참고.

## 통계 백필 (`scripts/crawl_munpia_stats.py`)

작품 상세·회차 호출 없이 **목록 페이지만** 순회해 좋아요(`good_count`)/선호작(`prefer_count`)/댓글수/평점 등을 수집하는 저비용 크롤러. 전체 2,444페이지를 훑으면 실측 1~3시간이 걸림(2026-08-11 스냅샷 59분, 08-12 스냅샷 3시간 12분). 본 크롤(`crawl_munpia.py`)과 출력 디렉토리(기본 `data/raw/stats/`)·체크포인트가 분리돼 있어 **동시에 실행해도 서로 영향이 없음**.

```bash
uv run python scripts/crawl_munpia_stats.py --section nv.free --max-pages 1   # 소규모 테스트
uv run python scripts/crawl_munpia_stats.py --section nv.free --max-pages 0 --delay 0.8   # 전체 실행
```

`--resume` 없이 실행하면 **새 `run_id`로 새 스냅샷**을 만듦(시계열 확보용). `--resume`을 붙이면 중단된 스냅샷을 이어받음.

`novel-detail` 상세 API의 `likeCount`/`preferenceCount`와 개념적으로 같은 지표를 이 파일(`novel_stats_{run_id}.csv`)만으로 얻을 수 있음 — 컬럼 정의는 [데이터 사전](05_데이터사전.md) 참고.

## 정기 스냅샷 운영 (2026-08-13 확정)

**월 1회, 목록 앞 200페이지만** 새 `run_id`로 찍음.

```powershell
uv run python scripts/crawl_munpia_stats.py --max-pages 200 --delay 0.8
```

`--max-pages`는 절대 페이지 번호이므로 이 한 줄이면 되고 **코드 수정이 필요 없음**. `--resume`을 붙이지 않는 것이 핵심 — 붙이면 새 스냅샷이 아니라 직전 스냅샷을 이어씀.

### 왜 월 1회인가 — 일 단위는 측정상 노이즈였음

기존 2시점(`20260811_165552` ↔ `20260812_121713`, 실측 간격 21.4시간)의 델타:

| 대상 | `hit_count`가 변한 작품 | 일일 델타 중앙값 |
|---|---|---|
| 전체 48,795건 | **5.0%** | 0 (99% 분위수도 3) |
| 추론셋(앞 10화 확보) 11,139건 | 9.8% | 0 |
| 지지구간 내 1,790건 | 12.9% | 0 (90% 분위수 1.1) |

지지구간 작품의 **일일 조회수 증가율 중앙값은 0.000%**임. 이 속도면 5% 변화까지 193일, 10%까지 385일이 걸림. 하루 간격으로 찍으면 87%가 전 필드 0인 행만 쌓임.

원인은 무료 코퍼스가 사실상 방치작 더미이기 때문임. `serialization_status`는 전부 "연재중"으로 찍혀 있지만 실제 마지막 회차 게시 경과일 중앙값은 추론셋 **582일**, 지지구간 **3,204일(약 9년)**임. 30일 내 신규 회차가 올라온 작품은 추론셋의 11.0%뿐임.

조회수는 신규 회차와 함께 들어오므로 게시 주기보다 촘촘히 찍을 이유가 없고, 스냅샷은 현재 모델의 피처가 아니라 향후 자산이므로([로드맵](04_로드맵.md) "다중 시점 대비") 최신성 요구도 낮음.

### 왜 앞 200페이지인가 — 목록이 최신순 정렬임

목록 순위와 마지막 회차 경과일의 **스피어만 상관 0.998**:

| 페이지 | 경과일 중앙값 | 30일 내 갱신 비율 |
|---|---|---|
| 1~100 | -1 ~ 8일 | ~100% |
| 101~300 | 59일 | 13.1% |
| 301~800 | 361일 | **0.0%** |
| 801~2,444 | 1,528~3,565일 | 0.0% |

30일 내 갱신된 2,486건의 **99%가 첫 126페이지** 안에 있음(전체 2,444페이지). 200페이지는 여유분을 둔 값이고, 301페이지 이후는 30일 내 갱신 비율이 0.0%라 재크롤 가치가 없음. 이 범위 축소로 회당 비용이 **1~3시간 → 3분대**가 됨.

**전체 코퍼스(2,444p) 재크롤은 정기적으로 하지 않음.** 죽은 꼬리 구간이 필요해지면 그때 `--max-pages 0`으로 1회성 실행함.

### 자동화 (설계만, 등록은 추후)

회당 3분대라 `watch_and_resume.ps1` 워치독은 불필요함(워치독은 시간 단위 크롤용). Windows 작업 스케줄러로 충분함.

`scripts/monthly_snapshot.ps1` — 작업 디렉토리 이동 + 실행 + 종료 코드 로깅만 하는 얇은 래퍼:

```powershell
$ErrorActionPreference = 'Stop'
$root = Split-Path -Parent $PSScriptRoot
Set-Location $root
$stamp = Get-Date -Format 'yyyy-MM-dd HH:mm:ss'
uv run python scripts/crawl_munpia_stats.py --max-pages 200 --delay 0.8
"$stamp exit=$LASTEXITCODE" | Add-Content -Encoding utf8 "$root\data\raw\stats\monthly_snapshot.log"
```

등록(경로는 실제 클론 위치로 바꿔 쓸 것):

```powershell
schtasks /Create /TN "MunpiaMonthlySnapshot" /SC MONTHLY /D 1 /ST 04:00 `
  /TR "powershell -NoProfile -File <repo>\scripts\monthly_snapshot.ps1"
```

## 재개(resume) 동작 방식

`--resume`은 `--output-dir`의 가장 최근 체크포인트를 찾아 같은 `run_id`로 이어씀. 이미 처리된 novel_id는 건너뛰므로 중복 수집이나 중복 CSV row가 발생하지 않음. `--resume` 없이 실행하면 새 `run_id`로 처음부터 시작함(통계 크롤에서 **새 스냅샷**을 만들 때 이렇게 씀).

**`--start-page`로 재스캔 비용 줄이기**: `--resume`만 쓰면 목록을 항상 1페이지부터 다시 훑음. 이미 처리한 구간이라 수집은 안 하지만 **페이지 요청 딜레이는 그대로 듦** — 48,000건 규모에서 절반쯤 진행된 상태로 재개하면 건너뛰는 데만 20분 이상 걸림. 중단 지점을 알면 `--start-page`로 건너뜀.

```bash
# 34,064건까지 처리된 상태에서 재개 (20건/페이지 → 약 1,703페이지)
uv run python scripts/crawl_munpia_stats.py --section nv.free \
  --max-pages 0 --start-page 1700 --delay 0.8 --resume
```

- 시작 페이지는 `처리 건수 ÷ 20`에서 **여유를 두고 조금 앞**으로 잡음(중복은 체크포인트가 걸러줌)
- ⚠️ 목록 정렬이 크롤 도중에도 바뀌므로, 건너뛴 구간으로 밀려온 작품은 놓칠 수 있음. 정확도가 중요하면 `--start-page` 없이 돌리고, 끝난 뒤 커버리지 warning으로 누락 규모를 확인할 것
- `--max-pages`는 시작 페이지 기준 개수가 아니라 **마지막 페이지 번호**임(`--start-page 1700 --max-pages 1800` → 1700~1800)

**⚠️ 체크포인트는 `--output-dir` 단위임.** `CrawlCheckpoint.find_latest`는 해당 디렉토리의 `.processed_novel_ids_*.log` 중 **mtime이 가장 최근인 것**을 고름. 성격이 다른 크롤(무료 본크롤 / 통계 백필 / 유료 라벨 크롤)은 반드시 `--output-dir`를 분리해야 하며, 같은 디렉토리를 쓰면 `--resume`이 엉뚱한 체크포인트를 집어 데이터가 섞임. 통계 백필이 `data/raw/stats/`, 유료 크롤이 `data/raw/paid/`를 쓰는 이유임.

**알려진 한계 — 중단 시점에 따른 중복 작품 행**: `runner.py`는 작품 행 → 회차 행 → 체크포인트 순으로 기록함. 작품 행을 쓴 직후·회차 행을 쓰기 전에 예외가 나면 체크포인트가 남지 않아, `--resume` 시 같은 작품이 한 번 더 append됨(회차 저장 실패는 디스크 부족이나 스키마 가드 발동 정도로만 발생). 트랜잭션을 도입하는 대신 **검증으로 잡는 쪽**을 택함 — `scripts/validate_raw_data.py`의 `novel_id` 중복 검사가 error로 보고하므로 크롤 종료 후 항상 검증을 돌릴 것.

## 실제 사이트 조사 결과 (2026-08-10~11 기준)

- **robots.txt**: `www.munpia.com`은 `/novel/viewer/`(유료 열람 뷰어) Disallow, `mm.munpia.com`은 `/app_api/` Disallow. 그 외 크롤링 대상 경로는 모두 허용
- **⚠️ 목록 페이지네이션 주의**: `mm.munpia.com/?menu=novel&action=list&section=nv.free&page=N` 형태의 일반 GET은 `page` 값과 무관하게 **항상 1페이지와 동일한 내용**을 반환함. 실제 페이지네이션은 사이트 JS(`view_list()`)가 호출하는 AJAX 엔드포인트로만 동작함:
  ```
  GET mm.munpia.com/?ajx=1&menu=novel&action=list&section=nv.free&keyword=&page={page}
  Header: X-Requested-With: XMLHttpRequest
  ```
  응답은 HTML이 아니라 JSON(`{"list": [...], "page": N, "last": 전체페이지수, "count": 전체작품수}`)이며, 작품 ID는 각 항목의 `nvSrl` 필드. 목록 크롤링을 다시 구현할 일이 있다면 반드시 이 엔드포인트를 쓸 것 — HTML을 그대로 파싱하면 항상 같은 페이지만 반복 조회하게 됨
- **작품 상세/회차 API** (`www.munpia.com`, 비공식/역공학 — 공식 문서 없음):
  - `GET /api/v1/pc/novel-detail/{novel_id}` → `result.novelInfo`에 `title`, `authorName`, `genres`(문자열 리스트), `tags`(`{id,title}` 객체 리스트 — `title`만 join), `viewCount`, `chapterCount`, `createdAt`, `finish`/`pause`(불리언 — 완결/중단 상태를 여기서 파생시킴, 별도 status 문자열 없음)
  - `GET /api/v1/pc/novel-detail/{novel_id}/chapters?order=ENTRY_FIRST&page=N&size=100` → `result.list`(⚠️ `chapters` 아님)에 회차 배열. 각 항목의 `id`가 episode_id, `num`이 회차 순번, `free`(불리언)로 무료/유료 여부 판단(`accessType` 문자열 없음), `viewCount`/`likeCount`/`commentCount`는 그대로 사용 가능
- **인코딩**: 현재 구현은 목록·상세·회차 모두 JSON 엔드포인트만 쓰므로 인코딩 오인식 이슈가 없고, 코드에도 `response.encoding` 지정이 없음. HTML을 파싱할 일이 생기면 그때 `response.encoding = "utf-8"`을 명시할 것(Content-Type에 charset이 없어 `requests`가 인코딩을 오인식함)
- **작품 제목·회차 제목에 U+FEFF(BOM 문자)가 섞여 있는 경우가 있음** — 파일 손상이 아니라 작가가 입력한 원본 문자열임(회차 제목 624건, 작품 제목 1건). 화면 표시 단계에서 `str.strip("﻿")`으로 제거함(`scripts/build_app_bundle.py`)

## 테스트

```bash
uv run pytest
```

129개 단위 테스트가 entity 매핑, 목록 JSON 파싱, 상세/회차 수집(`fetch_novel_bundle` — 페이지네이션·스키마 변경 감지·차단 전파), 크롤 오케스트레이션(`run_crawl` — limit/skip/abort/resume), CSV append(BOM 중복 없음·스키마 가드), 체크포인트 저장/재개, robots.txt 경로 차단, 데이터 품질 검증, 피처·타겟·스키마·모델 파이프라인·앱 추론 로직을 덮음. 실제 네트워크 호출은 하지 않고 가짜 클라이언트를 주입하며, 위 API 스키마는 실제 소규모 크롤로 수동 검증됨. 항목별 분포는 [로드맵 E](04_로드맵.md) 참고.

## 데이터 품질 검증

```bash
uv run python scripts/validate_raw_data.py            # data/raw/ + data/raw/stats/ 기본
uv run python scripts/validate_raw_data.py --prefix paid_ --data-dir data/raw/paid --stats-dir data/raw/paid   # 유료 크롤 결과
```

가장 최근 `novels_*.csv`를 찾고, **거기서 뽑은 `run_id`와 같은 `episodes_*.csv`를 짝지어** 검증함(mtime으로 각각 고르면 서로 다른 run이 섞여 참조 무결성 검사가 무의미해지므로). `novel_stats_*.csv`는 본 크롤과 run_id·디렉토리가 분리돼 있어 `--stats-dir`에서 따로 찾음.

| 검사 | 대상 | 수준 |
|---|---|---|
| ID 중복 | `novel_id`, `episode_id` | error |
| 음수 값 | 조회수/좋아요/선호작/구매수/글자수 등 | error |
| 참조 무결성 | episodes → novels 고아 행 | error |
| 결측 비율 30% 초과 | 제목/작가/장르/평점 등 | warning |
| novels ↔ novel_stats 커버리지 | 양방향 누락 건수 | warning |

error 이슈가 있으면 종료코드 1. 수집 완료된 데이터 기준 error 0건, warning 2건(커버리지 항목). CSV 컬럼 정의는 [데이터 사전](05_데이터사전.md) 참고.
