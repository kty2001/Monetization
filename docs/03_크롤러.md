# 크롤러

문피아 무료 자유연재 목록의 작품/회차 메타데이터를 수집해 `data/raw/`에 CSV로 저장한다.

## 실행

```bash
uv run python scripts/crawl_munpia.py --max-pages 1 --novel-limit 5   # 소규모 테스트
uv run python scripts/crawl_munpia.py --max-pages 2500 --novel-limit 1000000 --delay 0.8 --resume   # 전체 크롤
```

| 옵션 | 기본값 | 설명 |
|---|---|---|
| `--max-pages` | 1 | 목록 페이지 최대 크롤링 수 (안전을 위한 기본값, 실제 전체는 약 2,442페이지) |
| `--novel-limit` | 10 | 상세정보를 수집할 최대 작품 수 |
| `--output-dir` | `data/raw` | CSV 출력 디렉토리 |
| `--delay` | 1.2초 | 요청 간 지연 시간(초) |
| `--resume` | off | `--output-dir`에서 가장 최근 체크포인트를 찾아 이어서 실행 |
| `--log-level` | INFO | `DEBUG`로 실행하면 요청별 타이밍 확인 가능 |

## 아키텍처

- `clawler/` — HTTP·오케스트레이션만 담당 (파일 I/O 없음)
  - `config.py` — `CrawlConfig`: 엔드포인트/헤더/딜레이/재시도 설정, `FORBIDDEN_PATH_PREFIXES`로 robots.txt Disallow 경로를 코드 레벨에서 원천 차단. `section` 필드(기본 `nv.free`)로 목록 카테고리를 바꿀 수 있다 — 아래 "섹션별 목록" 참고
  - `http_client.py` — `MunpiaHttpClient`: 요청마다 딜레이, 5xx/타임아웃 재시도(tenacity), 403/429는 재시도 없이 즉시 `BlockedByServerError`. `BlockedByServerError`/`ForbiddenPathError`는 작품 하나의 문제가 아니므로 skip 대상에서 제외되고 크롤 전체를 중단시킨다(`CrawlSummary.aborted`)
  - `list_crawler.py` — 목록 페이지를 1페이지부터 순회. `iter_list_pages`(novel_id만) / `iter_list_page_items`(구매수 등 원본 필드 포함 전체 item dict)
  - `detail_crawler.py` — 작품 상세 + 회차 목록을 가져와 `Novel`/`Episode` 엔티티로 변환. 응답에서 `result.novelInfo` / `result.list` 경로를 못 찾으면 `UnexpectedResponseError`를 던진다 — API 스키마가 바뀌었을 때 빈 값 행을 조용히 쌓지 않기 위함(작품 단위로 skip되어 `skipped_novel_ids`에 남고 WARNING 로그가 즉시 뜬다)
  - `checkpoint.py` — `CrawlCheckpoint`: 처리 완료된 novel_id를 append-only 로그(`data/raw/.processed_novel_ids_{run_id}.log`)에 기록해 재개 지원
  - `runner.py` — 전체 흐름 조율, 작품 단위로 CSV에 즉시 append (중단돼도 그때까지 수집분은 보존됨)
- `entity/` — JSON 응답 → dataclass 매핑 (방어적 `.get()` 파싱, 네트워크 없이 단위 테스트 가능): `Novel`, `Episode`, `NovelStats`(목록 API의 구매/대여/조회 집계 필드)
- `repository/` — dataclass → CSV 저장. `CrawlRepository(run_id, base_dir, prefix="")` — `prefix`로 무료/유료 크롤 출력을 분리 가능 (`data/raw/novels_{run_id}.csv` vs `data/raw/paid_novels_{run_id}.csv`)

## 섹션별 목록 (`section` 파라미터)

목록 AJAX 엔드포인트는 `section` 값에 따라 다른 카테고리를 반환한다. 확인된 값:

| section | 의미 | 규모 | 구매/대여 수(`nvSumPurchased`/`nvSumRented`) |
|---|---|---|---|
| `nv.free` | 무료 자유연재 (수집 완료) | 48,836건* | 항상 0 |
| `nv.pro` / `nv.regular` | 작가연재 / 일반연재(무료 단계) | 3,070 / 15,862건 | 항상 0 |
| `pl.serial` | 선연재(독점 유료), 진행 중 | 1,212건 | 채워짐 (단, 진행 중이라 계속 증가하는 censored 값) |
| `pl.serial_end` | 완결 유료 | 9,249건 | 채워짐 (확정값) |

\* 규모는 목록 API가 응답에 담아주는 `count` 값(크롤 **시작 시점** 스냅샷)이다. 실제 수집 결과는 **48,897건**으로 61건 많은데, 17시간에 걸친 크롤 도중 신규 작품이 등록되며 목록이 늘어난 결과다. 두 숫자가 다른 것은 정상이며, 재크롤 시에도 정확히 일치하지 않는다.

`pl.serial`/`pl.serial_end`는 구매수 예측 모델의 라벨(타겟) 데이터 소스로 쓸 계획 — 상세는 [로드맵](04_로드맵.md) 참고.

## 통계 백필 (`scripts/crawl_munpia_stats.py`)

작품 상세·회차 호출 없이 **목록 페이지만** 순회해 좋아요(`good_count`)/선호작(`prefer_count`)/댓글수/평점 등을 수집하는 저비용 크롤러. 전체 페이지를 다시 훑어도 30분대(0.8초 딜레이 기준)면 끝난다. 본 크롤(`crawl_munpia.py`)과 출력 디렉토리(기본 `data/raw/stats/`)·체크포인트가 분리돼 있어 **동시에 실행해도 서로 영향이 없다**.

```bash
uv run python scripts/crawl_munpia_stats.py --section nv.free --max-pages 1   # 소규모 테스트
uv run python scripts/crawl_munpia_stats.py --section nv.free --delay 0.8 --resume   # 전체 실행
```

`novel-detail` 상세 API의 `likeCount`/`preferenceCount`와 개념적으로 같은 지표를 이 파일(`novel_stats_{run_id}.csv`)만으로 얻을 수 있다 — 컬럼 정의는 [데이터 사전](05_데이터사전.md) 참고.

## 재개(resume) 동작 방식

목록 페이지 자체는 재개 시 항상 1페이지부터 다시 스캔한다(페이지 요청 자체는 저비용). 이미 처리된 novel_id는 체크포인트로 건너뛰므로 중복 수집이나 중복 CSV row는 발생하지 않는다. `--resume` 없이 실행하면 새 `run_id`로 처음부터 시작한다.

**⚠️ 체크포인트는 `--output-dir` 단위다.** `CrawlCheckpoint.find_latest`는 해당 디렉토리의 `.processed_novel_ids_*.log` 중 **mtime이 가장 최근인 것**을 고른다. 성격이 다른 크롤(무료 본크롤 / 통계 백필 / 유료 라벨 크롤)은 반드시 `--output-dir`를 분리해야 하며, 같은 디렉토리를 쓰면 `--resume`이 엉뚱한 체크포인트를 집어 데이터가 섞인다. 통계 백필이 기본값 `data/raw/stats/`를 쓰는 이유이고, 유료 크롤도 `data/raw/paid/`로 분리할 계획이다([로드맵 A](04_로드맵.md) 참고).

**알려진 한계 — 중단 시점에 따른 중복 작품 행**: `runner.py`는 작품 행 → 회차 행 → 체크포인트 순으로 기록한다. 작품 행을 쓴 직후·회차 행을 쓰기 전에 예외가 나면 체크포인트가 남지 않아, `--resume` 시 같은 작품이 한 번 더 append된다(회차 저장 실패는 디스크 부족이나 스키마 가드 발동 정도로만 발생). 트랜잭션을 도입하는 대신 **검증으로 잡는 쪽**을 택했다 — `scripts/validate_raw_data.py`의 `novel_id` 중복 검사가 error로 보고하므로, 크롤 종료 후 항상 검증을 돌릴 것.

## 실제 사이트 조사 결과 (2026-08-10~11 기준)

- **robots.txt**: `www.munpia.com`은 `/novel/viewer/`(유료 열람 뷰어) Disallow, `mm.munpia.com`은 `/app_api/` Disallow. 그 외 크롤링 대상 경로는 모두 허용.
- **⚠️ 목록 페이지네이션 주의**: `mm.munpia.com/?menu=novel&action=list&section=nv.free&page=N` 형태의 일반 GET은 `page` 값과 무관하게 **항상 1페이지와 동일한 내용**을 반환한다. 실제 페이지네이션은 사이트 JS(`view_list()`)가 호출하는 AJAX 엔드포인트로만 동작한다:
  ```
  GET mm.munpia.com/?ajx=1&menu=novel&action=list&section=nv.free&keyword=&page={page}
  Header: X-Requested-With: XMLHttpRequest
  ```
  응답은 HTML이 아니라 JSON(`{"list": [...], "page": N, "last": 전체페이지수, "count": 전체작품수}`)이며, 작품 ID는 각 항목의 `nvSrl` 필드. 목록 크롤링을 다시 구현할 일이 있다면 반드시 이 엔드포인트를 사용할 것 — HTML을 그대로 파싱하면 항상 같은 페이지만 반복 조회하게 된다.
  - 확인된 전체 규모: 무료 자유연재 **48,836건**, **2,442페이지** (조사 시점의 `count` 값 — 실제 수집 결과 48,897건과 다른 이유는 위 "섹션별 목록" 각주 참고)
- **작품 상세/회차 API** (`www.munpia.com`, 비공식/역공학 — 공식 문서 없음):
  - `GET /api/v1/pc/novel-detail/{novel_id}` → `result.novelInfo`에 `title`, `authorName`, `genres`(문자열 리스트), `tags`(`{id,title}` 객체 리스트 — `title`만 join), `viewCount`, `chapterCount`, `createdAt`, `finish`/`pause`(불리언 — 완결/중단 상태를 여기서 파생시킴, 별도 status 문자열 없음)
  - `GET /api/v1/pc/novel-detail/{novel_id}/chapters?order=ENTRY_FIRST&page=N&size=100` → `result.list`(⚠️ `chapters` 아님)에 회차 배열. 각 항목의 `id`가 episode_id, `num`이 회차 순번, `free`(불리언)로 무료/유료 여부 판단(`accessType` 문자열 없음), `viewCount`/`likeCount`/`commentCount`는 그대로 사용 가능
- **인코딩**: 조사 초기에 HTML 파싱을 검토했을 때는 Content-Type에 charset이 없어 `requests`가 인코딩을 오인식하는 문제가 있었다. **현재 구현은 목록·상세·회차 모두 JSON 엔드포인트만 쓰므로 이 이슈가 없고, 코드에도 `response.encoding` 지정이 없다.** HTML을 파싱할 일이 생기면 그때 `response.encoding = "utf-8"`을 명시할 것.
- **작품 제목·회차 제목에 U+FEFF(BOM 문자)가 섞여 있는 경우가 있다** — 파일 손상이 아니라 작가가 입력한 원본 문자열이다(회차 제목 624건, 작품 제목 1건). 정제 단계(`service/`)에서 `str.strip("﻿")`로 제거할 것.

## 테스트

```bash
uv run pytest
```

64개 단위 테스트가 entity 매핑, 목록 JSON 파싱, 상세/회차 수집(`fetch_novel_bundle` — 페이지네이션·스키마 변경 감지·차단 전파), 크롤 오케스트레이션(`run_crawl` — limit/skip/abort/resume), CSV append(BOM 중복 없음·스키마 가드), 체크포인트 저장/재개, robots.txt 경로 차단, 데이터 품질 검증을 덮는다. 실제 네트워크 호출은 하지 않고 가짜 클라이언트를 주입하며, 위 API 스키마는 실제 소규모 크롤로 수동 검증됐다.

## 데이터 품질 검증

```bash
uv run python scripts/validate_raw_data.py            # data/raw/ + data/raw/stats/ 기본
uv run python scripts/validate_raw_data.py --prefix paid_ --data-dir data/raw/paid --stats-dir data/raw/paid   # 유료 크롤 결과
```

가장 최근 `novels_*.csv`를 찾고, **거기서 뽑은 `run_id`와 같은 `episodes_*.csv`를 짝지어** 검증한다(mtime으로 각각 고르면 서로 다른 run이 섞여 참조 무결성 검사가 무의미해지므로). `novel_stats_*.csv`는 본 크롤과 run_id·디렉토리가 분리돼 있어 `--stats-dir`에서 따로 찾는다.

| 검사 | 대상 | 수준 |
|---|---|---|
| ID 중복 | `novel_id`, `episode_id` | error |
| 음수 값 | 조회수/좋아요/선호작/구매수/글자수 등 | error |
| 참조 무결성 | episodes → novels 고아 행 | error |
| 결측 비율 30% 초과 | 제목/작가/장르/평점 등 | warning |
| novels ↔ novel_stats 커버리지 | 양방향 누락 건수 | warning |

error 이슈가 있으면 종료코드 1. 현재 데이터 기준 error 0건, warning 2건(아래 커버리지 항목). CSV 컬럼 정의는 [데이터 사전](05_데이터사전.md) 참고.
