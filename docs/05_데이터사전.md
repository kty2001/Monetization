# 데이터 사전

`data/raw/`에 생성되는 파일들의 컬럼 정의. 원본 API 필드명과의 매핑은 [크롤러](03_크롤러.md)의 "실제 사이트 조사 결과"도 함께 참고.

## `novels_{run_id}.csv` (`entity/novel.py`)

| 컬럼 | 타입 | 원본 필드 | 설명 |
|---|---|---|---|
| novel_id | str | `id` | 작품 고유 ID |
| title | str | `title` | 제목 |
| author | str | `authorName` | 작가명 |
| genres | str | `genres`(리스트 join) | 장르(콤마 구분) |
| tags | str | `tags[].title`(join) | 태그(콤마 구분) |
| chapter_count | int | `chapterCount` | 총 회차 수 |
| total_view_count | int | `viewCount` | 누적 조회수 |
| like_count | int | `likeCount` | 좋아요 수 — ⚠️ run_id=`20260810_231806` 중 처음 36,145행은 `NaN`(엔티티에 필드가 없던 시점에 수집), 이후 12,752행부터 값 있음(크롤 도중 필드 추가 후 재개하며 스키마가 섞여 CSV가 깨졌던 것을 복구한 결과 — 아래 참고). 좋아요/선호작만 필요하면 `novel_stats_{run_id}.csv`(같은 크롤 기간에 전체 작품 대상으로 백필됨) 쪽이 더 완전함 |
| preference_count | int | `preferenceCount` | 선호작(구독) 등록 수 — 위와 동일 |
| serialization_status | str | `finish`/`pause`(파생) | `연재중`/`연재중단`/`완결` |
| created_at | str | `createdAt` | 최초 등록 시각 |
| crawled_at | str | — | 크롤 시각(ISO, KST) |
| run_id | str | — | 크롤 실행 ID(`YYYYMMDD_HHMMSS`) |

**수집 현황 (run_id=`20260810_231806`, 2026-08-12 검증)**

| 항목 | 값 |
|---|---|
| 작품 수 | 48,897 (novel_id 중복 0) |
| 회차 수 | 431,782 (episode_id 중복 0, 고아 행 0) |

| 회차가 0개인 작품 | 7,881 — 전부 `chapter_count == 0`인 실제 빈 작품이며 수집 실패가 아님 |

> **알려진 이슈(복구됨)**: 2026-08-12, 진행 중인 크롤을 재개하며 `Novel`에 `like_count`/`preference_count`를 추가한 코드가 함께 반영되는 바람에 `novels_20260810_231806.csv`가 11필드(구)/13필드(신) 행이 섞인 채로 깨졌었다. 필드 수 경계(36,145행/12,752행)가 정확히 일치해 데이터 손실 없이 복구(구 행은 두 컬럼 `NaN`으로 채움). 재발 방지로 `repository/csv_writer.append_csv`가 기존 헤더와 새 컬럼이 다르면 즉시 예외를 던지도록 가드를 추가했다(`tests/test_csv_writer.py`) — 진행 중인 크롤의 엔티티 스키마는 앞으로도 바꾸지 않는 것이 원칙이지만, 실수로 바꾸더라도 이제는 조용히 깨지는 대신 바로 에러로 드러난다.

## `.processed_novel_ids_{run_id}.log`

크롤 재개(`--resume`)를 위한 체크포인트. 한 줄에 처리 완료된 `novel_id` 하나씩(append-only). 상세는 [크롤러 — 재개 동작 방식](03_크롤러.md#재개resume-동작-방식).

## `novel_stats_{run_id}.csv` (`entity/novel_stats.py`, `scripts/crawl_munpia_stats.py`)

목록 API(`section=nv.free`/`pl.serial`/`pl.serial_end` 등)에서 얻는 좋아요/선호작/댓글/구매·대여 등 집계 필드. 작품 상세·회차 호출 없이 목록 페이지만 순회하므로 저비용(`scripts/crawl_munpia.py`/`crawl_munpia_paid.py` 본 크롤과 완전히 분리된 파일·체크포인트, 기본 출력 위치도 `data/raw/stats/`로 분리).

```bash
uv run python scripts/crawl_munpia_stats.py --section nv.free --delay 0.8 --resume
```

| 컬럼 | 타입 | 원본 필드 | 설명 |
|---|---|---|---|
| novel_id | str | `nvSrl` | 작품 고유 ID |
| section | str | — | 수집 대상 섹션(`nv.free`/`pl.serial`/`pl.serial_end`) |
| entry_count | int | `nvSumEntry` | 총 회차 수 |
| comment_count | int | `nvSumComment` | 총 댓글 수 |
| score | float | `nvSumScore` | 평점 |
| purchased_count | int | `nvSumPurchased` | **총 구매 수 — 예측 타겟(`target_paid_events`)의 원천** (`nv.free`는 항상 0). 매출은 여기에 회차 단가(사용자 입력)를 곱해 환산하며, 단가는 크롤·모델 어디에도 들어가지 않는다 |
| rented_count | int | `nvSumRented` | 총 대여 수(타겟에는 미사용, `nv.free`는 항상 0) |
| hit_count | int | `nvSumHit` | 누적 조회수(무료+유료 기간 합산 — 유료작 피처로 직접 사용 금지, [로드맵](04_로드맵.md)의 누수 방지 원칙 참고. `nv.free`는 순수 무료 기간 값) |
| good_count | int | `nvSumGood` | **좋아요/추천 수** — `nv.free`에서도 실값 확인됨(예: 적영검존 3) |
| prefer_count | int | `nvSumPrefer` | **선호작(구독) 등록 수** — `nv.free`에서도 실값 확인됨 |
| char_count | int | `nvSumChar` | 총 글자 수 |
| genre_main / genre_sub | str | `nvGnMain`/`nvGnSub` | 장르 코드(숫자 — 문자열 장르명은 `novel-detail` 상세 호출로 별도 확보) |
| is_finished / is_adult / is_exclusive | bool | `nvOptFinish`/`nvOptAdult`/`nvOptExclusive` | 완결/성인/독점 여부 |
| crawled_at / run_id | str | — | 크롤 시각 / 실행 ID |

`novels_{run_id}.csv`와 `novel_id`로 join 가능. `novel-detail` 상세 API의 `likeCount`/`preferenceCount`(위 `novels_*.csv` 표 참고)와 개념적으로 같은 지표를 목록 API 쪽(`nvSumGood`/`nvSumPrefer`)에서도 얻을 수 있어, 상세 API를 다시 호출하지 않고도 이 파일만으로 좋아요/구독 지표를 확보할 수 있다.

> **⚠️ join 시 양방향 누락 (2026-08-12 확인)**: `novel_stats_20260811_165552.csv`(48,864건)와 `novels_20260810_231806.csv`(48,897건)는 완전히 겹치지 않는다.
>
> - stats에만 있고 novels에 없는 작품: **31건**
> - novels에만 있고 stats에 없는 작품: **64건** → join하면 이 64개 작품은 `good_count`/`prefer_count`가 결측이 된다
>
> 원인은 두 크롤 사이(하루 간격)에 신규 등록/삭제가 있었고, 목록 API의 정렬 순서가 크롤 도중에도 바뀌기 때문이다(같은 이유로 전체 페이지를 훑어도 소수가 새어나간다). 치명적이지 않으므로 `scripts/validate_raw_data.py`는 **warning**으로 보고한다. 정제 단계에서 inner join으로 64건을 버릴지, left join으로 결측 처리할지 결정할 것.
